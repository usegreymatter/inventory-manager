# Inventory Manager reference guide

The short introduction is the [README](../README.md). This guide covers **v1.3.0-beta** and is the full reference for settings, CLI, CSV import, Odoo, the Hermes Desktop plugin and number rules. See the [current beta notes](release-notes/v1.3.0-beta.md) for safety changes and limits.

Inventory Manager estimates how long current stock may last using recent monthly net sales. It includes a fully synthetic sample, generated by `scripts/generate_sample.py` (seed 731209), accepts a local CSV, and has an optional read-only Odoo source. Forecasts are estimates, not promises or purchase orders.

## From Odoo/Excel in 5 steps

1. **Export current stock.** From your Odoo product/stock list (or your Excel stock sheet), export product name, stock on hand and unit of measure. Include Internal Reference/product code when available; use the same code in every report. Supplier and supplier lead time are optional. Use available-to-sell stock, or include the reserved/allocated quantity and review the stock-meaning choice on import. Odoo menu names and exportable fields depend on your version and permissions.
2. **Export sales quantities.** Export a sales/delivery report with product code, date and net quantity sold for at least three complete months. Use actual sales quantities, not revenue, quotations or cancelled orders; account for returns consistently. Stock and sales must use the same unit. A stock-only Odoo export is not enough.
3. **Shape one sheet in Excel.** Group net quantities by product and calendar month, then join those totals to the stock rows by exact product code. Name monthly columns `YYYY-MM`, for example `2026-08,2026-09,2026-10`. Keep one row per product and no grand totals. Use explicit `0` only for a verified month with no sales; a blank is not evidence of zero. Product codes can be omitted only when names uniquely identify products; repeated names need distinct codes. Save as UTF-8 CSV or `.xlsx`. The first-screen English/Arabic-header templates show the small monthly-column layout.
4. **Import and review.** Open the offline page, choose **Use your own file**, and inspect column matches, the first products, set-aside rows, units and warnings. Confirm units and acknowledge flagged risks only after checking them. **Data through** is the latest sales month, not today or a fresh stock count. Import does not repair missing data or partial months.
5. **Check open POs, then copy or print.** Compare the draft with Odoo Purchase orders/reporting filtered to confirmed orders still awaiting receipt (remaining quantities, not original ordered quantities). This page does not fetch or import an open-PO report. If incoming is absent, estimates count it as 0 and warn you to subtract existing orders before buying. An existing `on_order` quantity column can be included after reconciling units and remaining quantities; undated on-order stock is assumed within lead time for purchase guidance, not physical run-out. Choose **Import / settings → Print order** for the current full order list grouped by supplier, or **Copy order**. Printing/saving PDF is local; nothing sends an order or updates Odoo.

## Settings

In the shipped Arctic page, open **Settings** from the tools menu for Ordering, Safety stock, Alerts and collapsed Advanced EOQ controls. **Add safety stock to orders** defaults on; toggling it updates the selected-product before/after preview and order quantity immediately.

Open a supplier's **Settings** action for shared overrides, or the selected product's **Info → Product settings** for product-specific values. Each field inherits **product > supplier > file > global default**, with provenance labels and Custom markers. Blank scoped values or Reset reveal the next source; global defaults do not overwrite values already supplied by a file.

The supported override fields in `engine.py`'s `OVERRIDE_FIELDS` are:

- **Supplier:** lead time (`supplier_days`), MOQ (`minimum_order`), pack size (`pack_size`), ordering/review interval (`review_days`) and model service target (`service_level`).
- **Product:** all five supplier fields, plus order cover (`months_of_cover`, 0–36 months), unit cost (`unit_cost`), profit-based suggestion opt-in (`profit_suggestion`), sale price (`sale_price`), total shelf life (`shelf_life_days`), age on arrival (`arrival_age_days`), minimum remaining life (`min_remaining_life_days`) and salvage percentage (`salvage_pct`). See [profit-based suggestions](PROFIT-ORDER.md) and [shelf-life rules](SHELF-LIFE.md) for their effects and limitations.

For a product's total shelf life, JSON `null`, numeric `0` or string `"none"` explicitly disables an inherited cap. An absent override inherits; Reset removes the override. An explicit no-cap value is not a missing value and does not remove actual lot-expiry facts.

Arctic settings persist locally per dataset, without persisting CSV contents unless you explicitly opt in below. **Export settings** and **Import settings** transfer validated JSON; invalid imports leave current settings untouched. The Python CLI accepts the same file:

```sh
python3 stock_runway.py inventory.csv --all --today 2026-11-01 --settings inventory-manager-settings.json
```

See [Settings control](history/changes/settings-control.md) for exact ranges, defaults, reset behavior and a recomputed sample comparison. The Desktop JavaScript core and Python engine resolve the same inputs; formulas and no-override golden outputs are unchanged.

### Industry setup guides

In Settings → **Industry starting points** (Desktop: All settings), the General, Grocery/food, Pharmacy, Fashion/seasonal, Spare parts and Electronics buttons are **setup guides for ordering rhythm and shelf-life prompts**, not amount optimizers. Check **How often do you place orders?** against the existing `review_days`; edit Ordering first if it is wrong. The guide preserves that interval and prompts you to enter verified shelf-life facts only for applicable products; it does not guess or write global shelf-life assumptions.

**Industry buttons do not change order amounts on their own from General defaults.** A confirmed ordinary-setting change can affect quantities: the cover floor can raise insufficient cover, and General can reset a custom forecast method, buffer or service target. Review the old → new settings and before/after quantity impact, then Apply or Cancel. Only insufficient per-product cover is raised to that product’s review interval, without adding lead time again; other overrides stay unchanged. Undo restores the previous settings until a settings/dataset change or reload.

Pharmacy no longer automatically selects 99% service after that proposal failed the independent synthetic gate. Other than an explicit General reset, guides preserve the user's service target. The remaining guides matched General quantities at 7- and 30-day ordering cadence in the synthetic gate; this is **not** evidence of superior ordering, guaranteed service or real-world performance. Exact recipes, cover-floor rules, no-shelf-life semantics and archived evidence: [Industry setup guides](PRESETS.md).

Select rows or all filtered rows for **Copy order**, **Export CSV**, or Clear. Selections remain selected across filters. Unknown incoming remains blank. `arrives_by` is deliberately blank in worklist exports: this view does not derive a new-order arrival date. Text cells are protected against spreadsheet formulas. No action sends or places an order.

Estimates count unknown incoming as 0; blank exported incoming is still unknown, not confirmed zero. For partly known incoming, retain the known amount and still check for missing orders. Passing a copied list or CSV to a colleague does not remove this caveat.

## Chat tool

The single `stock_runway` tool works in CLI, Telegram, Desktop, and other Hermes chat surfaces.

```json
{"source":"sample","horizon":6,"skus":["SEAL-CLR-300"]}
```

With Current, the basic forecast uses the average of the latest three full months; with enough history it can follow last year's seasonal pattern scaled to recent sales. Monthly demand stays fractional throughout calendar demand calculations, rather than being rounded up each month. The legacy physical forecast rounds current stock down; purchase guidance retains exact source stock and rounds only the final purchase to whole units or the configured MOQ/pack. Projected stock subtracts forecast demand and adds confirmed receipts. The physical forecast's run-out month is the first month-end at or below zero; its run-out day estimates the crossing within that month. Error grades compare four held-out months against a three-month average. They are a small historical check, not a guarantee.

The horizon is 1–12 whole months (integral JSON numbers such as `6.0` are accepted). With no SKU filter, more than 50 results are limited to the 50 soonest run-outs, followed by valid items without a run-out and then held items; the response includes `truncated: true` and `total_count`. Summary lines match the returned items. The disclosure counts only positive receipts included in those items' selected forecast horizon; held items do not contribute receipts. `order_overdue` is true only when the estimated order-by date is before the as-of date, not when it equals that date. A backtest with zero actual sales in its four checked months reports “No recent sales to check,” not a reliability grade.

### Planning and order export

#### Input meaning and acknowledgement

Every **single CSV** runs input review, whether or not interpretation flags are
supplied. Successful `--strict` imports also receive input review. It prints `Input meaning: {…}` JSON on
**stderr** with warnings, affected SKUs and acknowledgement reasons; it does not
mix review text into CSV/JSON stdout. Canonical `--bundle` input keeps its own
validation instead.

- `--show-orders-anyway`: acknowledge the reported input risks **after checking
  the file**. Without this flag, a review requiring acknowledgement stops before
  export with exit code **2** (no order output is written). This does not repair
  invalid rows, bypass row validation or guarantee a safe purchase.
- `--stock-includes-reserved`: subtract a recognised reserved/allocated quantity
  column from stock before planning. Contributing warehouse rows are netted at
  SKU level; only the aggregate available stock is floored at zero. Blank
  reserved means zero, with a warning; a warehouse with reserved greater than
  stock gets an oversold warning even when the SKU aggregate is positive. A missing
  reserved column or blank reserved cell warns that available stock may be overstated,
  naming the contributing sheet even if another warehouse supplies reserved quantities; invalid reserved
  quantities set affected rows aside and require acknowledgement. Do not use this
  flag if stock is already available-to-sell. It cannot be combined with
  `--strict`, which cannot recognise the extra reserved column.
- `--incoming-not-in-file`: ignore incoming in this file, retain
  `incoming_unknown` and count it as 0. Exported incoming remains unknown;
  separately supplied dated receipts are retained. The warning
  is **Incoming orders unknown — counted as 0. Check open POs before ordering.**

The two interpretation flags are rejected with `--bundle`. More than 20% of
source stock rows missing stock or sales, more than 20% of sales-ledger rows
missing quantity, future sales dates, a latest month still in progress,
mismatched stock/sales units, conflicting contributor lead times or units,
identical blank-location rows, or invalid reserved subtraction requires
acknowledgement. CSV conflicts use the same gate as workbook conflicts.

When compatible stock sheets are added together, Desktop and the offline page require
**Show orders anyway** after a named-sheet confirmation: **Stock from sheets X, Y was
added together. Confirm these are separate warehouses — not totals, copies or older
snapshots.** After import, a **Check before ordering** summary remains beside the
worklist. Shared file-wide warnings appear once there; a separate affected-product
list and **Input warning** row markers identify product-specific warnings. **Dismiss**
hides only that summary for the current in-memory import; the next accepted import
restores it. The product page/side panel keeps each
warning beside the order advice. Warning text is displayed literally, not as HTML.
Remove total
sheets, duplicate exports and older snapshots upstream; acknowledgement does not
de-duplicate them or change quantities. Exact cell-for-cell identical blank-location
rows also require acknowledgement: **Identical rows found for SKU … — possible
duplicate export**. Nonidentical blank-location rows still aggregate as Unspecified.

Exactly 20% does not trigger the missing-row threshold. Leading
blank sales months before the first nonblank sale count as **not yet launched**
(`not_yet_launched_cells`), not missing, and need no acknowledgement. All-blank,
internal and trailing blanks still count as missing. Long-format sales use the
first nonblank sale month per exact SKU across contributing warehouses too; joined
wide sales count as evidence, and absent auxiliary sales are guarded. Blank sales
cells remain zero in the numeric series; the classification is review-only. Affected
products also show **New product: N months before first sale ignored**. This is
informational: “ignored” means excluded from the missing-data count, not removed
from the sales series or forecast window. It does not by itself require
acknowledgement. All contributing stock/sales unit labels are checked without
inventing a conversion.
The current-month warning does not remove or change those sales or the forecast
maths; automatic exclusion is pending an owner decision.

Input review uses these warnings (`YYYY-MM` is the detected latest month):

- **Incoming partly unknown — known incoming retained; check open POs for every warehouse before ordering.** Known incoming is preserved with `incoming_unknown=true`; only explicit “Not in file” removes `on_order`.
- **Incoming orders unknown — counted as 0. Check open POs before ordering.**
- **Oversold: reserved exceeds stock in a warehouse — available stock is netted across contributing warehouses, then floored at 0. Check allocations before ordering.**
- **Sales and stock units disagree — convert both to the same unit before ordering.**
- **Latest month (YYYY-MM) is still in progress — partial sales may lower the forecast. Remove it or wait for month end.** This requires acknowledgement, independently of the future-month warning.
- **Reserved cell is blank — counted as 0; check allocations before ordering.**
- **Stock is blank but reserved is filled — available stock cannot be calculated.**

```sh
# Only after reviewing the reported risks:
python3 stock_runway.py stock.csv --show-orders-anyway --all
# Only if these descriptions match the export:
python3 stock_runway.py stock.csv --stock-includes-reserved --incoming-not-in-file --all
```

Exit **0** means export succeeded; exit **2** means acknowledgement is needed or
an argument, input or output error occurred. Read stderr to distinguish these
cases; do not automatically retry with acknowledgement in scripts.
`--explain` appends a `why_this_amount` CSV column; `--json` exports JSON including
the explanation and exact `why_breakdown` ledger. See [Why this amount](WHY-THIS-AMOUNT.md)
for display rounding versus exact quantities.

#### Order settings and output

Advisory stockout detection is separate from the existing exposure correction.
Use `--stockout-adjust` to opt order guidance into trailing-median replacements;
it defaults off and never changes the source sales. The exact contract,
limitations, reproducible sample/demo report and parity command are in
[Advisory stockouts](history/changes/stockout-advisory.md).

From this checkout, run the standard-library-only CLI without Hermes or Desktop:

```sh
python3 stock_runway.py stock.csv -o orders.csv
python3 stock_runway.py stock.csv --receipts receipts.csv --today 2026-11-12 --delivery-days 14 --months-of-cover 2 --service-level 0.95 --include-safety-stock --all
```

With `-o`, the short summary prints to stdout. Without `-o`, CSV goes to stdout (redirect with `> orders.csv`) and the summary goes to stderr to keep the CSV clean. By default, export the **Order now** and **Order soon** buckets, including zero-quantity supply-gap attention rows. `--all` includes every item, including unplannable items with a reason and blank purchase fields. Rows retain input order. Output columns are `sku,name,unit,status,order_qty,order_by,next_confirmed_delivery,arrives_by,run_out,on_hand,on_order,safety_stock,reorder_point,reason`; `status` is the shared bucket key (`order`, `running-low`, `healthy`, `overstocked`, `no-sales`, `needs-data`). Unknown incoming stays blank, not zero. Numeric columns use plain decimals without trailing `.0` or exponent notation. `order_by` is an ISO date or `now`; `run_out` is the physical run-out date. `next_confirmed_delivery` is the shared guidance's next gap-ending confirmed delivery (not necessarily the earliest receipt on file). `arrives_by` is the displayed `order_by` date (today for `now`) plus the guidance's already-rounded `lead_days`, an estimated lead-time arrival, **not** a confirmed supplier promise. It is separate from the physical purchase-cover window when undated incoming moves the displayed order date. Missing order dates/leads or out-of-range arrival dates stay blank. The CLI refuses to overwrite either input with `-o` (shell redirection is managed by your shell).

`--stock-date YYYY-MM-DD` is the date the stock on hand was counted. It applies to that run only and is not a settings key (a settings file containing `stock_counted_on` is refused). The count is treated as the stock at the **end of the count day**: sales on the count date are already out of it. Without `--stock-date`, stock is assumed counted on the last sales month end (`as_of`); when `--today` is more than 7 days later, stderr warns that sales after month end may be subtracted twice. With it, run-out, order-by and order quantity start from the count date: the counted stock is translated to the equivalent month-end balance using the same calendar demand the order guidance already uses (rounded toward less stock), so no other forecast or order maths changes. The date must be on or after the first day of the last sales month and not after today, otherwise the CLI refuses with exit 2. Items with lot quantities keep their stock and get a warning. For a count inside the last sales month, that month's sales after the count day are taken off the counted stock; if that month's sales are 0 (blank sales cells import as 0), nothing is taken off and the item warns that sales after the count may be missing from the file, so the stock was not reduced for them. A non-numeric last month keeps the stock with a warning; incoming stock due on or before the count date is still added on its date, with a warning. The browser has the same **Stock counted on** field under **Import / settings**; it applies to the loaded file only and resets when a new file is opened. Exports keep the counted stock in `on_hand`.

`--today` defaults to the local calendar date. `--delivery-days` sets the fallback for missing supplier lead time (default 14, whole days 1–3650); source lead times, including zero, take precedence. `--buffer-days` adds demand for 0–365 extra days to the purchase target (default 0). `--months-of-cover` accepts 0–36 (default 2); `--service-level` accepts 0.9, 0.95 or 0.99 (default 0.95). The `safety_stock` and `reorder_point` columns expose the engine estimates when calculable. Safety stock is added to orders by default, so service level can affect purchase quantities; `--include-safety-stock` explicitly enables the same default. To disable it, pass a settings JSON file with `"include_backup_in_orders": false`. It does not change physical run-out dates. CSV input and confirmed-receipt rules are the same as [Local CSV](#local-csv). Invalid arguments, unreadable files and output errors exit with code 2 and a short error, without a traceback. These are estimates, not purchase orders.

The summary reports how many items need data (`N items need data (use --all to include them)`), even when the default filter omits them. Sales data more than 45 days old prints the same freshness warning as `/stock`, on the summary stream rather than inside the CSV. File output via `-o` uses UTF-8 with a BOM (`utf-8-sig`) for Excel; stdout remains plain UTF-8. To reduce spreadsheet formula injection, every text cell beginning with `=`, `+`, `-`, `@`, TAB or CR is prefixed with a single quote. Numeric values are not escaped as text. This is export hardening, not a change to source identifiers or calculations.

CLI, chat and Desktop use the shared order-guidance policy for the same order dates when supplied the same CSV snapshot, planning date and settings. Desktop settings are saved locally and are not automatically shared with CLI or chat; legacy physical forecast dates are separate from order guidance. The tool adds `items[].guidance`, `items[].order_bucket` and `purchase_summary`; `/stock` adds the purchase lines after the existing physical forecast list. Legacy `summary`, `forecast()` results (including physical `order_by`) and the compact card are unchanged. Python callers can merge the source item and `forecast()` result with `as_of`, then call `engine.order_guidance(item, today, settings, as_of)` and `engine.order_bucket(...)` directly. `order_bucket(..., guidance=guidance)` reuses a computed guidance result. Purchase-only calculation failures produce a needs-data purchase line without replacing a valid legacy forecast.

Direct-call edge cases are explicit in the parity corpus: empty array/object `held` values count as held, as in JavaScript, and `monthly_sales=None` behaves like JavaScript's null history (no optional planning estimates). Two intentional Python hardenings are allowlisted with exact expected outputs: missing/null `receipts` safely means an empty map instead of Desktop's arithmetic-error fallback, and `today='0000-01-01'` is rejected as needs-data because Python's calendar has no year zero (Desktop's JavaScript date accepts it). Valid loaded CSV/sample inputs do not use either edge case. Guidance dates use fixed en-GB month names, including **Sept**; existing month labels remain unchanged.

## Phase 1 number rules

Monthly demand stays fractional through the complete calendar demand window.
Only the final purchase is rounded to whole units or the configured MOQ/pack.
This is calculation rounding, separate from two-decimal display formatting in
quantity explanations. A **display rounding** term reconciles the visible ledger
when needed; it does not change demand or the purchase. Fractional purchase targets
can retain up to six display decimals. JSON `why_breakdown` keeps the exact ledger;
see [Pure purchase-quantity explanation](WHY-THIS-AMOUNT.md).
Display status and order timing use the same calendar inventory-position crossing,
not snapshot stock divided by just next month's sales. Urgent order checks take
precedence over Overstocked. Reviewed before/after numbers are in
[`history/changes/phase1.md`](history/changes/phase1.md).

**Buffer days** defaults to **0**, whole days **0–365**. If set, the planner
adds forecast demand for those extra days once to the purchase target. It does
not move the safety-stock trigger or extend dated-receipt eligibility. Missing
or invalid saved settings use the current default; invalid explicit CLI or
slash flags are rejected. Use Settings, `settings={"buffer_days": 7}`, or CLI
`--buffer-days 7` to opt in. Zero cover disables replenishment.

Safety stock is included in orders and the trigger **by default**. Reorder point
is lead-time demand plus active safety stock. The order deadline is the first
inventory-position crossing of active safety stock minus delivery time. The
purchase protects every prefix of the arrival-to-cover window; a later receipt
cannot erase an earlier shortfall. Physical run-out uses physical stock and dated
confirmed receipts, not undated on-order stock. MOQ and pack rounding apply only
to positive need. The current [replenishment policy v2](history/changes/order-policy-v2.md)
supersedes earlier buffer, safety-stock and legacy-order-date descriptions.
Imported data is not saved by default. After a successful import, you can tick **Remember this file on this device** (unticked by default). The snapshot stays in this browser on this device; reload labels it **Restored from this device · imported <date>**. It is not live stock, and stale-sales warnings still apply. **Forget saved data** removes the saved snapshot immediately; the open data stays in memory until reload or close. Saved settings, layouts and local order lists are separate and are not removed by this control. Browser storage can be blocked, full or cleared; the app says when it cannot save, including files over its 2 MiB serialized-text limit (~4 MiB browser storage). Leave it off on shared devices. Buffer settings persist locally like delivery days.

## Local CSV

### Import check before replacing your products

The shipped Arctic page previews every CSV before import: **products ready**, source **rows set aside**, and **columns ignored**. Expand the matched-header map, ignored names, defaults, row numbers/reasons and warnings. **Import N products** replaces the current dataset; **Cancel** or Escape leaves it untouched. **Download set-aside rows (CSV)** includes the original columns plus source row/reason; spreadsheet-formula prefixes are escaped. This report and rejected rows stay in memory, not local storage. Lists render at most 100 entries at a time, with **Show next 100** for larger files.

**No SKU column?** Browser smart import, the CLI/MCP CSV loader and the Python spreadsheet-inspection helper share a safe fallback: generate stable local codes only when product names are unique after NFC normalization, Unicode casefolding and trimming. Repeated normalized names, including rows from different warehouses, stop the import and require a real product code column. An unrecognized column that looks like product codes also blocks the fallback; this includes numeric references under headers such as Ref or Article No. Rename that column to `sku` or `Item Code`, or map it explicitly in smart import. The preview discloses: “No product code column found — codes were made from product names.” Generated codes are local identifiers, not verified ERP or supplier references; check them before use. Renaming a product can change its generated code, so use real codes for durable product settings. Sharing this fallback does not establish full browser/Python spreadsheet header-mapper parity.

Python `sources.load_csv(path)` returns the same `import_report` structure as JavaScript `parseCsv(text)`: `matched` (`source` → `field`), `ignored`, `defaulted` (`field`, `value`, `reason`), `rows_imported` (usable source rows, including combined warehouses), `products_ready`, `rows_set_aside` (`row`, `reason`, original `values`), `warnings`, and `source_headers`. Row numbers refer to the original CSV lines, including blank lines. The CLI prints `Import check: {…}` as JSON to **stderr**, even with `-o`; exported CSV remains clean. `--strict` / `load_csv(path, strict=True)` / `parseCsv(text, {strict:true})` retain legacy whole-file row/numeric rejection instead of set-aside/clamping. Encoding and delimiter detection still run in strict mode.

Tolerant preflight also supplies `accepted_rows`: zero-based parsed-record indexes (header is index 0) identifying only the source rows that actually contributed. These are not physical CSV line numbers; quoted multiline cells and blank records must not shift contributor identity. Reserved subtraction and incoming-supply review use these contributors, not rejected rows or a reconstructed range.

#### Joined workbook facts and source evidence

Workbook input review uses the **canonical joined facts** that will be parsed for planning. Separately joined incoming, reserved stock and distinct stock/sales unit fields therefore participate in review; a joined PO total is not reported as absent just because the base stock sheet has no incoming column. Desktop and standalone smart preflight parse the adjusted canonical rows while retaining the original editable mappings and missing-field gates. Rebuilding canonical rows must not turn missing source mappings or unmatched auxiliary sales history into an importable zero-demand product.

Input-meaning warnings are de-duplicated and emitted in a fixed priority order shared by Python and JavaScript (`input-meaning-warning-order.json`), including per-product warnings in exports. Equal-priority messages use the same UTF-16 lexical tie-break in both runtimes, including Unicode sheet/product names. Source-sheet traversal cannot reorder the same risks. An already-available stock header retains its double-subtraction warning even if the reserved column comes from another sheet. When an exact-SKU allocations sheet without a stock column supplies a nonblank reserved quantity (including zero), that joined evidence clears the false “Reserved stock missing” flag for the SKU. Truly absent/blank reserved evidence still warns. A blank base stock value filled from another sheet is described as **filled**, not added together; an actual later warehouse addition is still disclosed.

Canonical arithmetic does **not** replace source-row safety evidence. Completeness counts, leading/internal/trailing blank classification, sales dates and every contributing stock/sales unit label remain source-based, so aggregation cannot hide a blank row or a unit mismatch. Warehouse-level oversold/blank-reserved warnings and invalid-reserved acknowledgement are retained too. When incoming is known for only some stock contributors, keep the known sum and mark incoming partly unknown; **Not in file** is the explicit choice that removes that sum.

Separate non-ledger stock-bearing sheets with compatible quantity columns are treated as warehouse sheets: exact-SKU joins sum **on-hand, reserved, on-order and monthly sales** (and historical receipts where supplied), with **Combined stock from sheets East, West** naming the contributors. Every affected product also retains **Stock from sheets East, West was added together. Confirm these are separate warehouses — not totals, copies or older snapshots.**, and import requires **Show orders anyway**. Identical-looking copies are also summed: remove duplicate exports before import. Incompatible quantity-column schemas are ambiguous, keep the base snapshot and require acknowledgement. Long sales ledgers carrying an on-hand snapshot never become an extra warehouse, in either base-sheet direction. When reserved subtraction is selected, subtract the aggregate reserved quantity from aggregate stock and floor only that SKU-level result at zero. Repeated stock/reserved snapshots in a long sales ledger are not added once per transaction. Conflicting supplier lead times or units keep the first/base value and require acknowledgement before ordering; acknowledgement does not resolve the conflict or convert units. Other metadata differences (including name, supplier, cost, MOQ and pack size) retain the first value and produce one informational summary, counting affected SKUs and showing at most ten shortened examples plus the remaining count. Check those retained values before purchasing. Individual messages are bounded and repeated messages are de-duplicated. Product-wide sales duplicated across warehouse exports must be corrected upstream. See [Review round 3](history/changes/review-round-3.md) for scope and verification status.

- Negative stock is set aside: **negative stock in ERP — fix count**. Blank references, inactive products, invalid numeric cells and malformed row widths are also set aside rather than blocking usable products. `Total`/`Grand Total` footer rows are reported but never treated as products. A file with no usable products is rejected; the page still offers its set-aside download.
- A negative net-sales month is clamped to zero, with a **returns exceeded sales in YYYY-MM** warning and affected-row count. Leading blank monthly sales cells before the first recorded sales value are classified as **not yet launched**, counted in `not_yet_launched_cells`, and excluded from the missing-sales count. Internal or trailing blanks (and rows with no recorded sales value) remain missing sales, not proof of zero demand. This classification is an import-review disclosure, not a new forecasting method or a change to the core maths.
- Repeated SKUs at distinct Warehouse/Location values sum **on-hand, on-order, monthly sales and historical receipts**; sales are explicitly summed even if identical across rows. First-row metadata is retained, mismatched stock units are set aside, and the report says **combined N warehouse rows**. If any warehouse rows are excluded, totals explicitly cover usable rows only. With a Warehouse/Location column present, blank cells mean **Unspecified**: all otherwise usable blank-location rows aggregate, including repeated blanks, with a warning to check for duplicate exports. Repeated rows at the same **named** location and duplicates with **no location column** are still set aside after the first usable row. A blank cell is not the same as an absent column. Review ERP export granularity: product-wide sales repeated on every warehouse row must be de-duplicated in the ERP first.
- Comma, semicolon and tab delimiters are detected from the unquoted header. Currency symbols, Western/Indian thousands grouping, space/NBSP/figure-space/narrow-NBSP thousands grouping and accounting parentheses are understood. In semicolon files a single comma means the decimal separator (`1,500` → 1.5); mixed European notation `1.200,50` → 1200.5 also works. Dot-only numbers remain decimal numbers. Lead times such as `2 weeks`, `3 days`, `1 month` become 14, 3, 30 days (a month is explicitly 30 days).
- UTF-8 (with/without BOM) and BOM-marked UTF-16 LE/BE are accepted. Invalid UTF-8, including cp1256 Arabic exports, fails clearly: **File is not UTF-8; re-export as CSV UTF-8**. The page decodes bytes strictly rather than importing replacement characters/mojibake.
- Odoo `Product/Vendors/Delivery Lead Time`, `Product/Vendors/Delay` and `Delay` map to supplier lead days. `MinOrdrQty` / `Min Qty`, `Pack` / `Qty per pack`, and `Cost` / `AvgPrice` / `Standard Price` populate the engine's already-supported per-product minimum order, pack size and unit cost. `Min Qty` here means minimum **purchase quantity**, not an ERP min-stock/reorder threshold; export the appropriate purchase field. Purchase UoM stays ignored with a warning: quantities must already use the stock unit. Expected Date is ignored with a warning; it does not establish confirmed incoming supply. `Active=FALSE` or `Inactive=TRUE` sets the product aside.

### Works with your ERP's export

You don't need to rename columns. Export your stock list with monthly sales from your ERP and load it as is — Inventory Manager recognises the usual column names from **SAP Business One, SAP S/4HANA, NetSuite, Zoho Inventory, QuickBooks, Microsoft Dynamics 365, Odoo and Sage**, in any order:

| Inventory Manager needs | Also accepted (examples) |
|---|---|
| `sku` | Item Code, ItemCode, Item number, Product Code, Internal Reference, Part Number, SKU |
| `name` | Item Name, Product name, Display Name, Description, Product/Service |
| `unit` *(optional, default "units")* | UoM, Unit of Measure, Usage Unit, Inventory unit, InvntryUom |
| `on_hand` | Qty On Hand, Quantity On Hand, Stock On Hand, OnHand, Available, In Stock |
| `supplier_days` *(optional)* | Lead Time, Lead Time (days), Vendor Lead Time, Purchase Lead Time |
| `category` *(optional)* | Category, Item Group, Product Category, ItmsGrpNam |
| `on_order` *(optional)* | On Order, Qty On Order, Quantity On Order, On PO, Open PO Qty, Incoming, Incoming Qty, Ordered Qty, Expected, In Transit |
| monthly sales | `2026-01`, `2026/01`, `01/2026`, `Jan 2026`, `January 2026`, `Jan-26` |

Unrecognised columns are ignored **and named in Import check**; recognised cost/MOQ/pack fields are used as described above. Numbers like `"1,200"` are read as 1200. Ready-made examples for each ERP are in [`erp-examples/`](erp-examples/). Existing valid item records remain unchanged.


The optional `category` column and `rcv:YYYY-MM` historical delivery columns may follow the five required prefix columns alongside the sales columns. If any `rcv:` column is supplied, supply exactly one for **every** sales month, including explicit `0` quantities for months with no deliveries. Duplicates, invalid/out-of-range months, partial coverage, blank quantities and negative/non-finite quantities are rejected consistently in Python and the browser. No `rcv:` columns means delivery history is absent, not zero. These historical columns do not add future receipts.

An optional `on_order` column belongs after `category` (or directly after `supplier_days` when category is absent), before the monthly sales columns. It is an undated incoming quantity in the same product unit as stock. Nonblank values must be finite, non-negative numbers no greater than **1,000,000,000,000**; use `0` for explicitly none. A blank cell or omitted column leaves the item's field absent, not an asserted zero. ERP exports may use any incoming alias above and any column order. For backward compatibility, an alias column whose nonblank cells all lack normalized numeric syntax (for example, `Expected` containing dates) is ignored. A literal canonical `on_order` column is never discarded this way; mixed numeric and invalid alias values are also rejected. Incoming is deducted from purchase quantities but never added to the physical stock projection or run-out date. Do not repeat the same supply in both undated `on_order` and dated confirmed receipts: both are deducted from a purchase calculation.

Pass an explicit local path with `source=csv` and `csv_path`. The first five columns must be `sku,name,unit,on_hand,supplier_days`; append at least three chronological, unique `YYYY-MM` columns containing monthly net sales. Leave `supplier_days` empty if unknown. Numeric values must be non-negative. Files are capped at 2 MiB and 10,000 item rows. An optional receipts CSV passed as `receipts_path` uses the exact columns `sku,month,quantity`; only listed confirmed receipts are added. Receipt months must be after the last sales month and no more than 12 months later. `csv_path` can read any local CSV the agent is pointed at; it is not restricted to the plugin directory. Paths are trusted local files selected by the user; this plugin does not write them. Do not pass files containing data you are not authorized to expose to Hermes.

The Hermes tool includes `import_report` and an import-count disclosure in its response. The legacy Desktop plugin upload and recovery paths keep strict whole-file rejection until they have an explicit preflight confirmation UI; the shipped Arctic page is the tolerant interactive import surface.

### Supported numeric and calendar bounds

Sales labels must be consecutive calendar months from **1000-01 through 9998-12** in both Python and JavaScript. The upper bound reserves a full 12-month forecast through year 9999; the lower bound preserves the existing 65,000-month history fixture (1000-01 through 6416-08) and ample order-date headroom. Supplier lead time is **0–3650 days** (empty means unknown). Source CSV errors identify the row and field. Direct engine/browser callers get held items for invalid labels, dates or values; unsupported horizons still produce a request error.

Each stock, sales-month, historical-delivery-month or future-receipt-month quantity is capped at **1,000,000,000,000** in product units. This is well above the normal 9,999,999 stress case. Duplicate future receipts must stay under the same monthly cap. Fake-Odoo-tested conversion, quant totals, net-sales totals, current-month rollback and incoming-delivery totals enforce that bound before converting Decimal values to floats. An out-of-range stock/sales item is held; a failure confined to incoming history omits the entire history map, preserving the existing unknown-history policy. Intermediate signed Odoo totals are also bounded, so a later offset cannot erase an earlier range failure.

Calculated sums, reconstructed balances and percentage ratios must remain finite and within an absolute **1e18** arithmetic bound. This accommodates the full supported history at the individual quantity cap (under 1.1e17 total) while stopping overflow and extreme ratios. An unexpected per-item calculation exception yields “Couldn't calculate: check this item's data.” without exposing exception text; other items remain usable. Missing or invalid delivery history remains explicitly unknown.

Small quantities show up to two decimals below 10; a smaller nonzero magnitude displays `<0.01` (with a minus sign for negative values). Forecast demand stays fractional; display formatting does not change calculations, and only the final purchase uses whole-unit or MOQ/pack rounding. Quality uses unrounded sales: existing integer percentages remain, but an error that would round to zero retains its nonzero value and displays `<0.01%` when needed. Exactly constant fractional sales have zero error.

## Odoo

Supported Odoo versions are 17, 18 and 19; unit conversion is tested against fake responses only, not live servers. Odoo is optional and read-only. Configure `ODOO_URL`, `ODOO_DB`, `ODOO_USER`, and `ODOO_API_KEY` using Hermes secret settings. The plugin never asks for credentials in its UI or chat. It requests only product name/code/unit/category and completed stock move fields needed for internal/customer/supplier movement calculations. It reads internal-location quants and rolls back subsequent completed moves to the last full month end. It reads location usage to classify internal, customer and supplier movements, and optional supplier delay fields only. It does not query partner records, customer records or prices. Odoo requires an explicit list of 1–50 SKUs and an HTTPS URL. Never point tests at a real Odoo server.

Only `search_read` is allowed for model reads; authentication is a separate handshake. The exact `ALLOWED_FIELDS` table is:

| Model | Fields |
| --- | --- |
| `stock.location` | id, usage |
| `stock.move` | product_id, product_uom_qty, product_uom, quantity, date, state, location_id, location_dest_id |
| `stock.quant` | product_id, quantity, location_id |
| `product.product` | id, name, default_code, uom_id, product_tmpl_id, categ_id |
| `product.supplierinfo` | product_tmpl_id, product_id, delay |
| `uom.uom` | id, factor, category_id, parent_path |

Move quantities are converted to the product unit when possible. Odoo 17/18 uses matching `category_id` values and `quantity / move.factor * product.factor`; Odoo 19 falls back from an invalid `category_id` field to `parent_path`, checks matching first path segments, and uses `quantity * move.factor / product.factor`. Unit reads include archived units with `context={"active_test": false}`; no other model accepts a context option. An item with an unconvertible sales/return or current-month stock rollback move is held with “Some moves use a unit that cannot be converted.” Invalid quantities in those moves retain their existing errors. A failure confined to a historical incoming supplier delivery omits that item's entire `historical_receipts` map, leaving otherwise valid net sales, stock and forecast usable. Internal transfers do not hold an item.

### Known limitations

- The same bounded completed-move read includes supplier-to-internal receipts for the history window, converted to product units. Supplier location usage is requested alongside internal/customer usage; the category display name comes from `categ_id`. With no supplier locations, incoming coverage is unknown and `historical_receipts` is omitted. With supplier locations and valid coverage but no historical deliveries, the complete map contains explicit zeros. Invalid history-only incoming quantities or unit conversions omit the entire item's map rather than publishing partial history; the UI requests delivery history. No purchase-order fetch is added. Existing future receipts remain the only future supply.

- The read-only Odoo adapter does not fetch open purchase orders and deliberately leaves `on_order` absent. That is unknown incoming supply, not a claim that nothing has been ordered. Use an authorized CSV export to supply this optional field; the Odoo read allowlist is unchanged.

- UTC month bucketing may differ from local business-month boundaries.
- Odoo 16 or older falls back to `product_uom_qty`, the planned quantity, when the completed `quantity` field is unavailable.
- Historical stock rollback assumes moves complete at their recorded move date; it cannot reconstruct unrecorded completion timing or earlier quant corrections.

## Desktop

The full-page Inventory Manager page places the **Order today** list directly after the title, before source controls. Its per-row order sentence is larger and bolder than the product/SKU and explanation. Each row gives the product name and SKU, suggested quantity (whole units or the configured pack size), order-by date and a short run-out/delivery explanation. Selecting a row opens that product. The product view begins with the same plain order answer, followed by the existing stock headline, chart and disclosures. Quantity means the amount to buy **on the displayed order date**. The planned date is the later of today and order-by; its endpoint adds whole supplier lead days and `ceil(months_of_cover × 30)` cover days. Forecast demand runs from the snapshot month-end through that endpoint, subtracting exact snapshot `on_hand` and confirmed receipts due after the snapshot through the endpoint (inclusive). Minimum/pack rounding applies only to positive need. Demand follows snapshot-anchored calendar months: a complete month consumes one monthly forecast, and a partial month consumes elapsed days divided by that month's actual length. The 30-day conversion sets the cover endpoint only; it is not a daily demand rate. Run-out is the first day projected balance reaches zero, using the chart's rounded-down opening stock and extending beyond the selected horizon. Every guidance calculation treats receipts as available from the start of their month, including today's balance and quantity-horizon receipts. The earliest crossing determines order-by, buckets and order answers even when a later receipt restores stock. Out-of-stock describes projected balance today; a temporary gap retains its original crossing date and names the later delivery month, quantity and unit. These projections do not claim observed current stock. Supplier fractions round up to whole delivery days. A stale snapshot displays “Stock figures as of <date>”; dates include the year. This is a local estimate, not a purchase order.

The product browser combines search, flat/type presentation and counted exclusive filters: Order now, Order soon, OK, Overstocked, No sales and Not enough history. Counts follow search and cover all matches before the browser’s visible 50-item cap. The Order today panel includes the Order now and Order soon matches and includes every matching row in a scrolling list, including zero-purchase attention rows. When empty, it names the earliest upcoming order date even if its quantity is zero. Bucket priority is Not enough history > Order now > Order soon > No sales > Overstocked > OK. Held products and products without a usable delivery-time estimate when no default is set appear under Not enough history with a reason. Advanced settings start collapsed and persist locally: default delivery time, months of cover, overstock threshold, editable urgent/running-low date windows, and product-specific minimum order and pack size. Reset removes product overrides as well as restoring defaults. Every numeric control keeps draft text during keyboard edits; valid values recompute immediately, optional blanks clear on blur, and invalid drafts retain the previous calculation with a visible error. Blurring a blank required field retains the blank draft and explains which previous value is still used. Fractional packs/minimums support 0.000001–1e12 with up to six decimal places. Exact decimal rounding never orders below a positive requirement or minimum; zero need ignores the minimum. Derived orders may exceed the 1e12 source-cell cap, up to safe decimal precision and the inherited 1e18 arithmetic bound (absolute order ceiling 9007199254740991). A zero purchase quantity can still mean a supply gap: out-of-stock items remain in Order now, with a selectable explanation instead of an Order 0 purchasing sentence. Empty stock with zero recent sales explicitly suggests no quantity; positive stock with zero sales in the last three months reaches No sales before Overstocked.

The full-page chart shows solid historical demand, outlined forecast demand, green monthly deliveries and month-end inventory. `historical_receipts` is a separate complete map of sales-history months to delivered quantities. Inventory is rebuilt backward from the dataset's exact `on_hand` at the last full month: `end[m] = end[m+1] + sold[m+1] - delivered[m+1]`. Raw negative balances remain available in the reconstruction result; only plotted values are clamped. One warning identifies the boundary before the latest negative historical balance. Future shortages are clipped visually at zero while the table retains the signed balance; confirmed deliveries may restore positive inventory. The sample's added receipt history is explicitly synthetic.

The latest historical balance is at Now, with no extra half-month plateau. If exact `on_hand` differs from rounded-down forecast stock, both values meet at the same Now coordinate and the caption explains the rounding; forecast numbers and runout dates are unchanged.

Search matches all loaded product names and SKUs before limiting results to 50 soonest run-outs. “By type” groups those visible results by category, with “Other” for missing categories; “All SKUs” presents the flat order. A notice gives matching and total counts when truncated. Past sales, the forward table (including Delivered), and forecast quality start collapsed in native keyboard-accessible disclosures. Current on-hand presentation scope and protocol limitations are recorded in `.scratch/A10-BUILD-REPORT.md`.

The unified package includes a native Desktop page at `/stock-runway`. The sample is available immediately. “Load CSV” parses the selected file in the browser; it does not upload it. CSV parsing and forecast evaluation complete before the new dataset is saved; rejected uploads retain the previous good CSV. Page and quick-view recovery controls handle invalid saved datasets and unexpected render failures, with usable **Back to sample data** and **Choose another file** controls. ### Optional inventory planning

Advanced settings → **Planning (optional)** adds safety stock, a reorder point and the most economical order size (EOQ) beside the unchanged forecast. The default is 95% service level, a 30-day review period and 20% annual holding cost. The service-level percentages are planning assumptions, not a guarantee against running out. Safety stock uses the sample standard deviation (n−1 divisor) of the latest 3–12 monthly sales: `ceil(z × demand swing × sqrt((delivery days + review days) / 30))`. The 30-day convention matches existing order cover. The order threshold adds safety stock to the seasonal calendar-month forecast over the next delivery period, prorating partial months from the stock snapshot date. These figures do not subtract stock or incoming deliveries: they describe a target, not a purchase quantity.

Most economical order size (EOQ) needs a positive **Cost per order (ordering cost)** and product-specific **Unit cost — what one unit costs you** (set on the selected product). Both costs must use the same currency. It uses the next 12 forecast months and `sqrt(2 × annual demand × ordering cost / (unit cost × holding percentage / 100))`, then rounds up to the smallest order and complete packs. Missing costs leave it blank; this is a cost-based estimate, not an automatic replacement for the suggested order. Unit cost is entered as a product override; CSV cost import is not included in this change.

**Add safety stock to suggested orders** is on by default. Turning it off removes safety stock from the trigger and purchase target; its informational estimate remains visible. Physical run-out dates are unchanged by the toggle. Purchase dates, quantities and status can change. Python callers can pass `settings=` to `forecast(...)`; the chat tool accepts the same `settings` object, including `product_overrides[sku].unit_cost`. Python's `suggested_order_quantity(...)` helper applies the same opt-in safety stock and exact decimal purchase rounding to a caller-supplied demand window; the Python forecast itself does not invent a new order-date policy. `/stock` includes short planning figures alongside its run-out list. Planning settings saved on Desktop are local to Desktop, not automatically shared with chat.

### Purchase safety and data freshness

**Missing-data gates.** Missing incoming supply stays unknown in source data and exports, but purchase estimates assume 0 incoming; check existing orders before buying. Missing or invalid stock or sales holds advice (at least 3 complete sales months are required). Missing supplier lead time uses the configured fallback (14 days by default, marked `used_default_lead`); clearing that fallback without another valid lead holds purchase advice, not the physical forecast. A supplied source lead of 0 is valid. Invalid supplied incoming holds advice.

`big_order_months` defaults to **6** and accepts **0.1–120** months independently of the overstock setting. A final rounded purchase is flagged `big_order` only when it is **strictly greater than** `monthly_demand * big_order_months`. This is the next forecast month's demand scaled to the selected months, not EOQ or an automatic cap. Review unusual purchases before placing an order.

In the browser, the **big-order warning is visible in both the worklist and product detail**, beside the purchase advice. It is a check-before-buying prompt, not a hidden settings-only flag or a cap on the suggested quantity. Check MOQ, pack size, cover and the sales history before acting.

The following additional warnings ask you to review unusual sales history; **they do not automatically remove sales, change the forecast method or reduce an order**:

- **Single-month sales spike:** with at least **4 months of history**, a month strictly above **4× the median of nonzero historical sales** triggers review. Zero months do not enter that median. Check whether the sale was a one-off, a bulk order or an import error before treating it as recurring demand. A spike is not proof of an error.
- **Possible dead stock:** at least **3 trailing months of zero sales** combined with a **positive suggested order** triggers a warning. Check that the product is still sold before replenishing it; this is not an automatic discontinuation decision.
- **Possible stockout-hidden demand:** **on_hand ≤ 0** and **zero sales in the latest month** triggers a warning. No stock may explain the lack of sales; zero observed sales is not proof of zero demand. This warning alone neither estimates lost sales nor turns on the optional stockout adjustment.

These are review heuristics, not validated diagnoses of demand. Inspect the source data and existing orders; acknowledgement or copying/exporting an order does not make its quantity safe.

Python preserves every numeric forecast field, status, date and JSON key (only planning wording changes) when neither `on_order` nor an explicit `settings.big_order_months` is supplied. Either opt-in adds `inventory_position`, `suggested_order`, `covered_by_on_order`, and `big_order`; supplied `on_order` is also retained. Inventory position is exact-decimal `on_hand + on_order`. Optional purchase planning follows Desktop's calendar algorithm: independently find physical run-out beyond the displayed horizon, plan the order at `max(today, physical_runout - ceil(delivery_days))`, then cover through that date plus `ceil(delivery_days) + ceil(months_of_cover * 30)` days. Demand is accumulated from the stock snapshot to that endpoint using each calendar month's daily rate; deduct exact stock, undated incoming and dated receipts due by the endpoint, optionally add safety stock, then apply smallest-order/full-pack rounding. Incoming reduces this physical target rather than moving it to the later inventory-position run-out. The default cover is 2 months. `forecast(..., today=...)` accepts an ISO date or `date`, defaults to `as_of` for deterministic calls, and changes only optional safety estimates, never legacy physical `order_by`, run-out or projections. Unknown delivery time, an unsupported calendar or unsafe purchase rounding leaves `suggested_order` null without holding the physical forecast. Call `suggested_order_quantity(..., on_order=quantity)` to apply the shared deduction/rounding formula to any caller-supplied demand window.

For a valid purchase plan, `covered_by_on_order` is true when positive incoming exists and `today + ceil(delivery_days) <= physical_runout`. Equality counts as on time; later or unknown delivery does not cover the gap. Coverage does not require a zero suggested purchase: incoming can cover the near-term gap while a purchase is still needed for the subsequent cover window. No-demand items without a physical demand crossing are not flagged. The physical run-out is still shown even when incoming covers it; undated supply is not a confirmed delivery date.

On Desktop, rows and item details show **N on order** for positive incoming. If no item supplies incoming data, a single dismissible tip reminds you to add it; dismissal is saved in local order settings. A physical shortage before the assumed incoming arrival remains a supply-gap/order warning, even when the incoming reduces the extra purchase to zero. The **Big-order check above (months of stock)** setting in **All settings** defaults to 6; oversized purchases display “Check this order: about N months of stock, much bigger than usual.” in the order row and detail.

Each **Order today** row has an **Already ordered / Not needed** menu: **Already ordered**, **Not selling anymore**, **One-off sale**, or **Other**. Skips are saved with the SKU, reason, skip date and data as-of date in local order settings. They hide the item for 14 days, or until a successfully loaded CSV has a later `as_of`, whichever happens first. **Show skipped (N)** reveals them with grey reasons and a **Restore** action. Skipping is a local reminder preference, not a purchase order or a change to your ERP stock. Skipped items remain available in the full product browser.

The chat tool always includes an item-level `big_order` boolean (false for held/unplannable items), even without safety opt-ins. In that case it computes the flag separately without exposing other safety fields or adding purchase figures to default summaries. It reports `data_age_days` from the **latest sales month-end** to the current local date, clamped to zero for future data, plus `sales_month` for the exact warning label. Tests and integrations can inject a `date` via `make_handler(today=...)`; the default reads live today on each call and passes that same date to purchase planning. Invalid sales months omit the optional freshness metadata rather than breaking held-item results. `/stock` warns only when data is **more than 45 days old**, with exactly: “Your sales data ends <Mon YYYY> (N days ago). Numbers may be out of date — load a newer file.” Age metadata does not change stock snapshots, forecast dates or the compact card schema; the injected/live date affects optional purchase quantities as described above.

## Slash command

`/stock` prints the run-out list with no model call. `/stock SKU1 SKU2` shows only those items, and `/stock path/to/file.csv` runs on your own CSV.

## Optional dated planning bundle (Phase 2 milestone)

Single CSV behavior is unchanged. Explicit local bundle imports add confirmed
incoming PO balances on their due dates. Late unresolved POs HOLD purchase approval
until reconfirmed. See [Phase 2 semantics and import commands](history/changes/phase2.md).
Use `stock_runway.py DIRECTORY --bundle --today YYYY-MM-DD`, tool `bundle_path`, or
convert the canonical sibling CSVs with `bundle_import.py DIRECTORY --today YYYY-MM-DD`
and choose its JSON output in Desktop/standalone. Do not put optional metadata into
stock.csv month columns. These calculations are local estimates, not purchase approval.
Confirmed customer orders in the optional bundle deplete stock on delivery dates.
Included orders consume that month's baseline once; incremental orders add to it.
Overdue balances become due on the planning day. Unknown or positive reservations
HOLD approval; explicit zero-reservation observations can unlock the dated scenario.
Reservation mapping/allocation remains outside this milestone. Review the Phase 2
policy and numeric examples before relying on these local estimates.
Optional complete `sales_history.csv` exposure and backorder observations now support
stockout correction through the same bundle path. Only verified lost sales uplift,
with a fourfold cap; censored months stay unobserved in the adopted baseline.
Raw sales and historical backtests remain unchanged. See the Phase 2 policy for
eligibility, holds and the raw/adopted trace. Manual demand percentages and future method selection stay off.
Complete explicit project flags in `sales_history.csv` can exclude verified one-off
months from the adopted baseline while preserving raw history and calendar labels.
The optional outlier check only suggests review; it never removes a month. At least
three eligible observations are required. Partial flags HOLD approval. See the
Phase 2 notes for independent exposure/project gates and exact numeric examples.
